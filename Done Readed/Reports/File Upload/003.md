# HackerOne - Stored XSS via Malicious PNG Upload in GitLab Wiki

[Original Report](https://hackerone.com/reports/880099)

---

## Overview: What Happened?

A vulnerability in **GitLab’s Wiki file upload functionality** allowed an attacker to upload an **SVG file disguised as a PNG image**, which led to a **Stored Cross-Site Scripting (XSS)** vulnerability.

The server failed to properly validate:

* The **file extension** (e.g., `.png`, `.jpg`)
* The **MIME type** (`image/png`, `image/svg+xml`, etc.)
* The **actual file content**

This allowed an attacker to upload a crafted SVG file containing JavaScript that executed when clicked from the Wiki page or accessed via the raw file endpoint.

---

## Methodology: Step-by-Step Attack Path

### 1. Accessing the Upload Feature

* The attacker logged in to a GitLab account.
* Navigated to a project and opened the **Wiki** section.
* Clicked **New Page**, then uploaded an image.

---

### 2. Uploading Malicious PNG File

* The attacker selected a file with `.png` extension but SVG content containing embedded JavaScript:

```xml
<?xml version="1.0" standalone="no"?>
<!DOCTYPE svg PUBLIC "-//W3C//DTD SVG 1.1//EN" "http://www.w3.org/Graphics/SVG/1.1/DTD/svg11.dtd">
<svg onload="alert(1)" xmlns="http://www.w3.org/2000/svg">
  <polygon id="triangle" points="0,0 0,50 50,0" fill="#009900" stroke="#004400"/>
</svg>
```

* Clicked **Create Page**, then clicked on the green triangle to trigger the XSS.
* In some cases, the user needed to click twice for the payload to fire.

---

### 3. Repeat via Raw File Upload

* The attacker uploaded the same file in the repository’s master branch.
* Accessed the file directly at:

```
https://gitlab.com/<user>/<project>/-/raw/master/1111111.png
```

* Opening this URL triggered JavaScript execution.

---

## Technical Explanation

The vulnerability stemmed from the backend’s failure to strictly enforce file validation rules:

* The server trusted the **file extension** instead of inspecting content.
* Files with `.png` extension but SVG content were rendered as `image/svg+xml`.
* No **sanitization** or `Content-Disposition: attachment` headers were applied.
* Both **Wiki rendering** and **raw file views** were vulnerable.

---

## Impact

* **Stored Cross-Site Scripting (XSS)** via uploaded images
* **JavaScript execution** in user browsers upon interaction
* Potential for **session hijacking**, **cookie theft**, or **phishing**
* Exploitable in both **Wiki pages** and **raw file views** of public projects

---

## Variants and Extended Scenarios

| Scenario                    | Description                                                       |
| --------------------------- | ----------------------------------------------------------------- |
| **SVG disguised as PNG**    | SVG content uploaded with `.png` extension                        |
| **Raw file endpoint abuse** | Accessing uploaded malicious file via `/-/raw/` endpoint          |
| **Multi-extension bypass**  | Using filenames like `xss.jpg.svg` or `xss.png.html`              |
| **MIME-type spoofing**      | Changing `Content-Type` to `text/html` or `image/svg+xml`         |
| **Null byte attacks**       | Filenames like `xss.jpg%00.svg` (if server mishandles null bytes) |
| **Polyglot files**          | Uploading files that are both valid images and valid HTML with JS |

## Checklist

Use this checklist to assess whether a file upload feature is vulnerable to XSS via SVG or HTML/JS injection:

| Step                                | Description                                                             | Status |
| ----------------------------------- | ----------------------------------------------------------------------- | ------ |
| **Upload Point Found**              | Locate image/file upload (Wiki, repo files, etc.)                       | 🔲     |
| **Fake PNG Upload**                 | Upload SVG content using `.png` extension                               | 🔲     |
| **Embed JavaScript Payload**        | Use `<svg onload=...>` or `<script>` inside SVG                         | 🔲     |
| **Intercept Request**               | Confirm MIME type not validated (can be `image/png`, but actual XML)    | 🔲     |
| **Trigger in UI**                   | Click or open file to execute payload                                   | 🔲     |
| **Raw File Execution**              | Access uploaded file via `/raw/` endpoint                               | 🔲     |
| **No Sanitization or Filtering**    | Check if browser renders file directly without escaping script          | 🔲     |
| **Check Headers**                   | Absence of `Content-Disposition: attachment` or restrictive CSP headers | 🔲     |
| **Try File Polyglots**              | Upload files that are both valid images and valid HTML (polyglots)      | 🔲     |
| **Check for SVG Injection**         | Attempt uploading SVGs with embedded scripts or event handlers          | 🔲     |
| **Test Null Byte Trick**            | Try names like `xss.jpg%00.html` (if applicable)                        | 🔲     |
| **Check Server Extension Handling** | See if the server executes/render files based on name or content        | 🔲     |
