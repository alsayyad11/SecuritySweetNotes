# HackerOne - File Upload XSS in Nextcloud Contact Image

[Original Report](https://hackerone.com/reports/808287)

---

## Overview: What Happened?

A vulnerability in the **image upload functionality** of the Nextcloud Contacts app allowed an attacker to upload and serve **malicious SVG files disguised as contact images**, resulting in a **Stored XSS (Cross-Site Scripting)** vulnerability.

The server failed to properly validate:

* The **file extension** (e.g., `.png`, `.jpg`, `.jpeg` only)
* The **MIME type** (`image/jpeg`, `image/svg+xml`, etc.)
* The **actual file content**

This allowed an attacker to upload a specially crafted `.svg` file containing JavaScript, which would then execute when the image was opened in a browser.

---

## Methodology: Step-by-Step Attack Path

### 1. Accessing the Upload Feature

* The attacker accessed a demo account via "Register with a provider > Demo > Take me there!"
* Navigated to the **contact image upload interface**
* Selected an SVG file containing JavaScript payload

---

### 2. Uploading Malicious SVG File

* The attacker uploaded the crafted `.svg` file through the contact image interface
* Once uploaded, they **right-clicked the contact image** and selected "Open image in new tab"
* The browser rendered the file as an inline image, and the **embedded JavaScript executed**, confirming Stored XSS

---

## Technical Explanation

The vulnerability stemmed from the backend's failure to enforce strict validation of uploaded file types. Specifically:

* The system did not **restrict allowed extensions** or MIME types for contact images
* Uploaded SVG files were rendered directly in-browser, allowing **execution of embedded JavaScript**
* No sanitization or `Content-Disposition: attachment` header was applied, allowing full rendering

---

## Impact

* **Stored Cross-Site Scripting (XSS)** on user profile/contact image
* **JavaScript execution** in the context of the app
* Potential for **session hijacking**, **credential theft**, or **phishing**
* **Security policy violation** due to content being served from trusted app UI

---

## Variants and Extended Scenarios

| Scenario                   | Description                                                              |
| -------------------------- | ------------------------------------------------------------------------ |
| **Multi-extension bypass** | Using filenames like `xss.jpg.svg` or `xss.png.html` to trick the server |
| **SVG with embedded JS**   | Uploading SVG files containing `<script>` tags                           |
| **MIME-type spoofing**     | Sending `text/html` content with `.svg` extension                        |
| **Null byte attacks**      | Filenames like `xss.jpg%00.svg` (if null byte is mishandled)             |
| **Polyglot files**         | Valid image files with hidden HTML/JS payloads                           |

## Checklist

Use this checklist to assess whether a file upload feature is vulnerable to XSS via HTML or script injection:

| Step                                | Description                                                                      | Status |
| ----------------------------------- | -------------------------------------------------------------------------------- | ------ |
| **Upload Point Found**              | Identify a file upload feature (profile image, document, form, etc.)             | 🔲     |
| **Client-side Validation**          | Check if validation is done only on the front-end (file extensions, MIME)        | 🔲     |
| **Extension Bypass Attempt**        | Try uploading `.html`, `.svg`, or `multi-extensions` like `.jpg.html`            | 🔲     |
| **Intercept Request**               | Use Burp Suite or a similar tool to modify request contents                      | 🔲     |
| **Content-Type Spoofing**           | Change `Content-Type` to `text/html`, `application/xhtml+xml`, etc.              | 🔲     |
| **Inject XSS Payload**              | Insert payload like `<script>alert(1)</script>` in the uploaded file             | 🔲     |
| **Check File Location**             | See if the file is accessible from a public/static directory                     | 🔲     |
| **Execution Test**                  | Open the uploaded file in browser — check if JavaScript runs                     | 🔲     |
| **Check Response Headers**          | Inspect if `Content-Type`, `Content-Disposition`, or CSP headers allow rendering | 🔲     |
| **Try File Polyglots**              | Upload files that are both valid images and valid HTML (polyglots)               | 🔲     |
| **Check for SVG Injection**         | Attempt uploading SVGs with embedded scripts or event handlers                   | 🔲     |
| **Test Null Byte Trick**            | Try names like `xss.jpg%00.html` (if applicable)                                 | 🔲     |
| **Check Server Extension Handling** | See if the server executes/render files based on name or content                 | 🔲     |
