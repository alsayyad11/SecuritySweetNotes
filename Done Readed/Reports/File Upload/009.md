# HackerOne - Stored XSS via Malicious Payload in CSV File Upload

[Original Report](https://medium.com/@vis_hacker/how-i-got-stored-xss-using-file-upload-5c33e19df51e)

---

## Overview: What Happened?

A vulnerability in a private bug bounty program allowed an attacker to trigger **Stored Cross-Site Scripting (XSS)** via the file upload feature, which accepted **CSV files**.

Although the server implemented **strict restrictions** to block common XSS vectors such as `<script>`, the attacker was able to bypass these protections using **non-traditional tags and advanced XSS payloads** inside a CSV file. When the data was rendered by the application, the malicious payload executed in the context of the page.

---

## Methodology: Step-by-Step Attack Path

### 1. Identifying the CSV Upload Feature

* The target application had a feature allowing users to **manually input data** or **upload a `.csv` file** containing contact information.
* The file was expected to include four columns:
  `firstname`, `lastname`, `company`, and `mobile number`.

---

### 2. Initial Attempts with Standard Payloads

* Uploaded a CSV file with typical XSS payloads like:

  ```html
  <script>alert(1)</script>
  ```

* Changed the `Content-Type` header to `text/html` using Burp Suite, but the server had protection against standard `<script>` tags, preventing execution.

---

### 3. Trying Alternative Payloads

* Attempted various non-script payloads and encodings, all blocked.

* Eventually discovered that the following **non-traditional XSS payload** successfully bypassed the filters:

  ```html
  </Textarea/</Noscript/</Pre/</Xmp><Svg /Onload=confirm(document.domain)>
  ```

* The payload worked because it exploited **HTML parsing quirks** using deprecated or less commonly filtered tags like `</xmp>` and `<svg>`.

---

## Technical Explanation

The vulnerability existed due to:

* **Inadequate sanitization** of user-uploaded CSV file content.
* The backend blocked obvious tags like `<script>`, but failed to handle other HTML vectors.
* The server **rendered the uploaded CSV data as HTML** in the browser without proper escaping or content filtering.

---

## Impact

* This is a **Stored XSS** vulnerability.
* When a privileged user or admin opened the page that displayed uploaded CSV data, the JavaScript payload executed automatically.
* The attacker could exploit this to:

  * Steal session cookies or tokens
  * Hijack accounts
  * Redirect users to phishing pages
  * Manipulate application behavior

---

## Variants and Extended Scenarios

| Scenario                  | Description                                                                |
| ------------------------- | -------------------------------------------------------------------------- |
| **Basic Script Blocked**  | Standard `<script>` tags were filtered by server                           |
| **Advanced Payloads**     | Payload using legacy HTML tags and SVG executed successfully               |
| **Stored in Database**    | Payload persisted in backend database and reflected in admin panel         |
| **Client-Side Execution** | JavaScript triggered in the context of the viewing user's browser          |
| **Blind XSS Potential**   | If logs or background processors rendered the payload without sanitization |

## Checklist

Use this checklist to test for XSS via file upload features:

| Step                             | Description                                                      | Status |
| -------------------------------- | ---------------------------------------------------------------- | ------ |
| **Upload Feature Found**         | Locate and access CSV upload interface                           | 🔲     |
| **Test Script Tags**             | Use `<script>` payloads and observe if blocked                   | 🔲     |
| **Try Legacy HTML Tags**         | Use tags like `</xmp>`, `</pre>`, `<svg onload=...>`             | 🔲     |
| **Check Storage Behavior**       | Confirm if the file content is stored and later rendered as HTML | 🔲     |
| **Observe Page Rendering**       | Watch where and how uploaded content is displayed in the app     | 🔲     |
| **Test with Special Characters** | Try payloads using encoded or obfuscated characters              | 🔲     |
| **Confirm Execution**            | Verify if the payload executes in the browser                    | 🔲     |
| **Inspect Sanitization**         | Check what characters or tags are being stripped or allowed      | 🔲     |
| **Review HTML Context**          | Understand where in the HTML structure the data is rendered      | 🔲     |
| **Attempt Blind XSS**            | Try sending payloads in areas not directly visible to attacker   | 🔲     |
