
# ASUS – Remote Code Execution via Unrestricted File Upload

[Original Post](https://www.mustafakemalcan.com/asus-rce-vulnerability-on-rma-asus-europe-eu/)

---

## Overview: What Happened?

A vulnerability in the **file upload functionality** on `rma.asus-europe.eu` allowed an attacker to upload **malicious ASP scripts** due to insufficient backend validation. The uploaded files were placed in a **publicly accessible `/uploads/` directory**, enabling **Remote Code Execution (RCE)** on the server.

This vulnerability was made possible because:

* File extension checks were enforced only on the **client-side**
* The backend failed to validate or sanitize the uploaded file
* The uploaded files were **publicly accessible**
* The server ran **Microsoft IIS 8.5**, which executes `.asp` scripts

---

## What is ASP and Microsoft IIS?

**ASP (Active Server Pages)** is a **server-side scripting language** developed by Microsoft. It allows dynamic content generation on web pages using `.asp` files, typically containing code written in VBScript or JScript. When a user accesses an ASP file on a web server, the server **executes the code** and sends the resulting HTML to the user's browser.

**Microsoft IIS (Internet Information Services)** is a popular **web server** software used to host websites and applications on Windows systems. It supports various scripting technologies including ASP, ASP.NET, PHP, and more. If an attacker uploads an `.asp` file to an IIS server, and that file is placed in a web-accessible location, it can be **executed directly by the server**—leading to Remote Code Execution if the script contains malicious commands.

## Methodology: Step-by-Step Attack Path

### 1. Discovering the Upload Feature

* While submitting a service form on `rma.asus-europe.eu`, the attacker found a file upload field intended for uploading **warranty documents**.

---

### 2. Bypassing Frontend Restrictions

* Initial attempts to bypass the file type restrictions failed.
* Upon inspecting the request in **Burp Suite**, the attacker noticed the restrictions were applied only on the **frontend**.
* Using a **null byte injection** technique and **modifying the request manually**, the attacker successfully bypassed the restriction.

---

### 3. Predicting the Upload Path

* After uploading the file, the next goal was to **find the directory** where files were stored.
* The path was discovered to be a predictable and publicly accessible location:
  `http://rma.asus-europe.eu/uploads/`

---

### 4. Achieving Remote Code Execution

* The attacker uploaded a **basic ASP shell** script (suitable for Microsoft IIS 8.5).
* Upon visiting the uploaded file via browser, the shell executed successfully.
* The attacker could now run arbitrary system commands on the ASUS web server.

---

## Technical Explanation

The core of this vulnerability lies in **unrestricted file upload**:

* **Lack of server-side validation** on uploaded files
* **No content-type or extension checks** on the backend
* Files were stored in a **web-accessible path**
* Uploaded `.asp` files were **parsed and executed by the server**
* Resulted in **arbitrary command execution** (RCE)

This kind of issue is especially critical when combined with a server like **IIS** that interprets script files.

---

## Impact

* Full **Remote Code Execution (RCE)** on ASUS’s server
* Attacker could potentially:

  * Exfiltrate sensitive data
  * Modify site content
  * Install persistent backdoors
  * Laterally move into internal systems
* This posed a **severe risk** to ASUS infrastructure and users

## Variants and Extended Scenarios

| Scenario                        | Description                                                  |
| ------------------------------- | ------------------------------------------------------------ |
| **Client-side only filtering**  | Relying on JavaScript or HTML input type validation          |
| **Null byte injection**         | Using `%00` or similar tricks to bypass filename filters     |
| **Executable file upload**      | Uploading `.asp`, `.php`, or other server-side script files  |
| **Publicly exposed upload dir** | Predictable and browsable `/uploads/` or similar directory   |
| **IIS/Apache parsing behavior** | Web server auto-executes uploaded scripts without validation |

## Checklist

Use this checklist when testing for file upload vulnerabilities:

| Step                                 | Description                                             | Status |
| ------------------------------------ | ------------------------------------------------------- | ------ |
| **Upload Feature Found**             | Locate file upload functionality                        | 🔲     |
| **Client-Side Filtering Bypass**     | Test for JavaScript-only file extension validation      | 🔲     |
| **Manual Request Tampering**         | Use Burp to upload disallowed file types (e.g., `.asp`) | 🔲     |
| **Test Null Byte Injection**         | Try payloads like `shell.asp%00.jpg`                    | 🔲     |
| **Determine Upload Path**            | Guess or brute-force where files are stored             | 🔲     |
| **Confirm Executable File Parsed**   | Visit uploaded `.asp` or `.jsp` and check if code runs  | 🔲     |
| **Run Command Execution Payload**    | Upload shell with system command execution capabilities | 🔲     |
| **Check Server Type**                | Identify if IIS, Apache, or Nginx is executing file     | 🔲     |
| **Search for RCE or File Inclusion** | Combine with other bugs like LFI or SSRF                | 🔲     |
| **Contact Vendor Responsibly**       | Report vulnerability to vendor or platform              | 🔲     |
