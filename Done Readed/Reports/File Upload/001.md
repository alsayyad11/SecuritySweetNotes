
# HackerOne - File Upload XSS in MoPub App Icon Upload Functionality

[Original Report](https://hackerone.com/reports/97672)

---

## Overview: What Happened?

A vulnerability in the **image upload functionality** of the MoPub platform allowed an attacker to upload and serve **HTML files disguised as images**, resulting in a **Stored XSS (Cross-Site Scripting)** vulnerability.

The server failed to validate:

* The **file extension** (e.g., `.jpg`, `.jpeg`)
* The **MIME type** (`image/jpeg` vs `text/html`)
* The **actual file content**

This allowed attackers to upload a malicious `.html` file and have it served from a trusted domain (`images.mopub.com`), making it possible to execute JavaScript in users’ browsers.

---

## Methodology: Step-by-Step Attack Path

### 1. Accessing the Upload Feature

* The attacker navigated to the **App Settings** section on MoPub’s dashboard.
* Selected a malicious HTML file and renamed it with a `.jpg` extension.

---

### 2. Intercepting and Modifying the Upload Request

* The attacker used a proxy tool (e.g., **Burp Suite**) to intercept the **HTTP POST** request for file upload.
* Modified the following values in the intercepted request:

  * Changed the **filename** from `.jpg` to `.html`
  * Modified the **Content-Type** header to `text/html`

---

### 3. Upload Succeeds Without Validation

* Despite the HTML content and incorrect MIME type, the server:

  * **Accepted** the file
  * **Stored it** on a public CDN (`https://images.mopub.com`)
  * **Served it** with `text/html` content-type

> This made the malicious file **accessible via browser** and allowed direct execution of its JavaScript content.

---

### 4. Triggering the XSS Payload

* When the attacker (or any user) visited the uploaded file’s URL, the browser rendered it as an HTML page.
* The embedded JavaScript executed automatically — confirming **Stored XSS**.

---

## Technical Explanation

The vulnerability occurred due to a **lack of proper server-side file validation**:

* **Only the filename extension** was validated on the client-side (not sufficient).
* The server failed to:

  * Inspect the **file signature / magic bytes**
  * Enforce MIME types based on content
  * Restrict content-type to safe image types (e.g., `image/jpeg`, `image/png`)
* The file was **served without any sanitization**, and no `Content-Disposition: attachment` header was used.

---

## Impact

* **Stored Cross-Site Scripting** on a trusted subdomain
* **JavaScript execution** in users' browsers
* **Possibility of phishing, session hijacking, or malware delivery**
* Violation of same-origin policies via a trusted CDN domain
* Potential reputational damage and user trust loss

---

## Variants and Extended Scenarios

| Scenario                   | Description                                                                |
| -------------------------- | -------------------------------------------------------------------------- |
| **Multi-extension bypass** | Using filenames like `xss.jpg.html` or `xss.html;.jpg` to trick the server |
| **SVG with embedded JS**   | Uploading SVG files containing `<script>` tags                             |
| **MIME-type spoofing**     | Sending `text/html` content with `.jpg` extension                          |
| **Null byte attacks**      | Filenames like `xss.jpg%00.html` (if null byte is mishandled)              |
| **Polyglot files**         | Valid image files with hidden HTML/JS payloads                             |

## Checklist 

Use this checklist to assess whether a file upload feature is vulnerable to XSS via HTML or script injection:

| Step                                | Description                                                                      | Status |
| ----------------------------------- | -------------------------------------------------------------------------------- | ------ |
| **Upload Point Found**              | Identify a file upload feature (profile image, document, form, etc.)             | 🔲     |
| **Client-side Validation**          | Check if validation is done only on the front-end (file extensions, MIME)        | 🔲     |
| **Extension Bypass Attempt**        | Try uploading `.html`, `.svg`, or `multi-extensions` like `.jpg.html`            | 🔲     |
| **Intercept Request**               | Use Burp Suite or a similar tool to modify request contents                      | 🔲     |
| **Content-Type Spoofing**           | Change `Content-Type` to `text/html`, `application/xhtml+xml`, etc.              | 🔲     |
| **Inject XSS Payload**              | Insert payload like `<script>alert(1)</script>` in the uploaded file             | 🔲     |
| **Check File Location**             | See if the file is accessible from a public/static directory                     | 🔲     |
| **Execution Test**                  | Open the uploaded file in browser — check if JavaScript runs                     | 🔲     |
| **Check Response Headers**          | Inspect if `Content-Type`, `Content-Disposition`, or CSP headers allow rendering | 🔲     |
| **Try File Polyglots**              | Upload files that are both valid images and valid HTML (polyglots)               | 🔲     |
| **Check for SVG Injection**         | Attempt uploading SVGs with embedded scripts or event handlers                   | 🔲     |
| **Test Null Byte Trick**            | Try names like `xss.jpg%00.html` (if applicable)                                 | 🔲     |
| **Check Server Extension Handling** | See if the server executes/render files based on name or content                 | 🔲     |
