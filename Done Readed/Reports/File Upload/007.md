# HackerOne - Stored XSS via Image File Name Reflection in FanFootage

[Original Report](https://hackerone.com/reports/93807)

---

## Overview: What Happened?

A vulnerability in **FanFootage's profile image upload functionality** allowed an attacker to upload a file with a **malicious file name containing JavaScript**, which led to a **Stored Cross-Site Scripting (XSS)** vulnerability.

The server failed to properly sanitize or encode the uploaded file name before rendering it in the UI, causing the JavaScript payload to execute in the browser of any user who viewed the affected page.

---

## Methodology: Step-by-Step Attack Path

### 1. Accessing the Upload Feature

* The attacker logged into their account on FanFootage.
* Navigated to the **Edit Profile** page where they could upload a profile image.

---

### 2. Crafting the Malicious File Name

* Renamed any file (even a non-image) to:

  ```
  "><svg onload=alert(1)>.jpg
  ```

* Uploaded this file as the profile picture.

---

### 3. Triggering the XSS Payload

* When the profile page was rendered, the server injected the file name into the HTML without sanitization.
* Browsers interpreted the payload as HTML, executing the embedded JavaScript.
* The payload worked in **Firefox** but was blocked in **Chrome** due to its built-in XSS protection filter.

---

## Technical Explanation

The vulnerability originated from:

* Reflecting the **raw file name** directly into the HTML of the profile page.
* No use of HTML encoding or escaping.
* Lack of input validation on the file name.

If a file name includes HTML/JS code and is rendered unsanitized in a browser, it can break the HTML context and allow JavaScript execution.

---

## Impact

* **Stored XSS** that affects all users viewing the affected profile.
* Can lead to:

  * **Session hijacking**
  * **Credential theft**
  * **Phishing**
  * **Malicious redirects**

---

## Variants and Extended Scenarios

| Scenario                       | Description                                                                     |
| ------------------------------ | ------------------------------------------------------------------------------- |
| **Malicious file name**        | File name contains HTML/JS payload                                              |
| **Non-image file upload**      | Payload does not require valid image file—any file type with crafted name works |
| **Browser-specific execution** | XSS blocked in Chrome but successful in Firefox or other browsers               |
| **Reflection into DOM**        | File name directly injected into HTML without sanitization                      |

---

## Checklist

Use this checklist to test for file name reflection–based XSS:

| Step                             | Description                                                             | Status |
| -------------------------------- | ----------------------------------------------------------------------- | ------ |
| **Upload Feature Found**         | Locate where user can upload files (e.g., profile image)                | 🔲     |
| **Inject JS in File Name**       | Rename file to include JavaScript code (e.g., `"><svg onload=...>.jpg`) | 🔲     |
| **Upload Malicious File**        | Submit file through the upload interface                                | 🔲     |
| **Check for Reflection**         | See if file name appears in rendered HTML                               | 🔲     |
| **Observe Execution in Browser** | Test in multiple browsers (Firefox, Chrome, etc.)                       | 🔲     |
| **Look for HTML Escaping**       | Confirm if file name is being properly encoded in the HTML              | 🔲     |
| **Attempt Polyglot Payloads**    | Try other injection formats (e.g., `<img src=x onerror=...>`)           | 🔲     |
| **Check DOM Context**            | Determine whether file name is injected into attributes, tags, etc.     | 🔲     |
