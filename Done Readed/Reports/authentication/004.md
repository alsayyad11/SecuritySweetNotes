
# HackerOne - 2FA Bypass Leading to Private Program Info Disclosure

[HackerOne Report](https://hackerone.com/reports/2486086)

---

## Overview: What Happened?

A vulnerability in the **2FA (Two-Factor Authentication)** enforcement logic on HackerOne allowed attackers to **bypass mandatory MFA** and gain access to **sensitive details of private programs**, including:

* Program descriptions
* Program scopes
* List of all invited/participating hackers

The bypass relies on setting up 2FA using the **Google Authenticator app** **without linking it to any Google account**, which lets the user trick the platform into thinking MFA is enabled — even though it’s not backed up or properly configured.

> After bypassing and accepting the invitation, the attacker could later disable and re-enable 2FA — and still regain access to the same private content again.

---

## Methodology: Step-by-Step Attack Path

### 1. Invitation Received

* The attacker received an **invite** from a private program (e.g., **Mondoo**).
* HackerOne requires enabling **2FA** before accepting any program invitation.

---

### 2. Setting up 2FA Without Valid Account

* The attacker installed **Google Authenticator** on a mobile device or emulator.
* During setup, they **skipped logging into any Google account**.
* Then, scanned the QR code from HackerOne and completed the setup locally.
* Even though no real account or backup exists, **HackerOne considered 2FA enabled**.

> This setup creates a **fake sense of security**: the platform thinks MFA is active, while the user could easily lose access or circumvent validation.

---

### 3. Accepting the Program Invitation

* With 2FA now “enabled,” the attacker accessed the invitation link.
* Successfully accepted the invitation.
* Got full visibility into:

  * Program rules and scope
  * Policy details
  * List of participating researchers

---

### 4. Disabling and Re-Enabling MFA

* The attacker then **disabled 2FA** via HackerOne account settings.
* Later, **re-enabled it**, this time linking it to a valid Google account.
* HackerOne **sent a new invitation email** for the same program (Mondoo).
* The attacker could accept it **again**, without losing any previous access.

---

### 5. Repeat Access Without Enforcement

* After re-accepting the new invite, the attacker accessed the same private data again.
* The **MFA transition** (from fake to real) did **not revoke previous access** or block reentry.

---

## Technical Explanation: How the 2FA Was "Faked"

Modern 2FA apps like **Google Authenticator** can function without any cloud backup or account linkage. This behavior was abused:

1. **Install the Authenticator app** on a clean or guest device.
2. **Skip** linking any Google account.
3. **Scan the QR code** shown during HackerOne's MFA setup process.
4. The app will start generating valid 6-digit codes locally.
5. HackerOne accepts this as a valid MFA setup, despite **no real identity or recovery option being configured**.

> This trick **fools the platform** into believing MFA is set up securely, while it is actually superficial and unverified.

---

## Impact

* **Access to private program data** without secure or validated 2FA
* **Persistent access** after disabling and re-enabling MFA
* **Leak of hacker participation lists**, which may aid targeted phishing or enumeration
* **Breakdown in intended access control logic** for private programs
* Violation of **trust assumptions** behind mandatory MFA policies

Use this checklist to test similar 2FA enforcement weaknesses in invite-based platforms:

| Step                   | Description                                           | Status |

| **MFA Setup**          | Attempt to set up 2FA via app without account linking | 🔲     |
|                        | Check if platform treats it as a valid MFA setup      | 🔲     |
| **Invitation Access**  | Accept invite and view private content                | 🔲     |

| **Disclosure Testing** | Look for exposure of private scopes, docs, or users   | 🔲     |
