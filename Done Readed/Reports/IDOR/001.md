

## IDOR to add secondary users in `www.paypal.com/businessmanage/users/api/v1/users`
**Reporter**: born2hack
**Link**: [https://hackerone.com/reports/415081](https://hackerone.com/reports/415081)

---

## Summary

This vulnerability was an **Insecure Direct Object Reference (IDOR)** in PayPal’s business account management system. It allowed a malicious user with a **PayPal Business Account** to add existing PayPal users—**who were not part of their business account**—as **secondary users** under their own business.

By doing so, the attacker could:

* Add arbitrary PayPal users to their business account without consent.
* Assign custom permissions to those users.
* Potentially gain unauthorized access to functions and sensitive data.
* Manipulate how PayPal handles the relationship between accounts and users.

PayPal awarded the researcher a **\$10,500 bounty** for identifying this flaw.

---

## PayPal Business Accounts and User Roles

* A **Business Account** in PayPal allows the owner to **add employees or team members** as **secondary users**.
* These users are assigned **roles and permissions**, allowing them to perform limited actions on behalf of the business (e.g., send money, view transactions, generate reports).
* Management of these users happens through both a **web interface** and **backend API**.
* The relevant API endpoint used in this report was:

```
POST /businessmanage/users/api/v1/users
```

This API endpoint is meant to allow a business owner to add users **within their organization only**.

---

## The Vulnerability Explained

The vulnerability stemmed from the **lack of proper authorization checks** in the backend.

Specifically:

* When submitting a request to add a secondary user, the attacker could provide a `user_id` or `email` that **belonged to a completely unrelated PayPal user**.
* The backend **did not validate** that the user being added actually **belonged to the same business account** as the attacker.
* As a result, the attacker was able to **add any existing PayPal user** as a secondary user under their own business.

This type of issue is classified as **IDOR**—where the application exposes or uses internal identifiers and fails to verify the caller's authorization to act upon them.

## Step-by-Step Breakdown

### 1. Attacker's Initial Setup

* The attacker registers or already owns a **PayPal Business Account**.
* From the PayPal dashboard, the attacker adds a **secondary user** normally, to observe how the API works.
* The attacker uses browser developer tools or Burp Suite to **capture the HTTP request** being sent to the backend.

Example observed request:

```http
POST /businessmanage/users/api/v1/users
Authorization: Bearer <access_token>
Content-Type: application/json

{
  "id": 12345678,
  "accessPoint": {
    "privileges": ["view_transactions", "send_money"],
    "id": 12345678
  },
  "roleName": "CUSTOM",
  "privilegeChanged": true
}
```

### 2. Modifying the Request

* The attacker **modifies the `id` field** in the request payload to refer to an arbitrary `user_id` that does **not belong** to their business account.
* This ID is likely **enumerable** (e.g., a sequential integer), making it guessable.

Modified request example:

```json
{
  "id": 87654321,  // user not under attacker's business
  ...
}
```

### 3. Sending the Exploit

* The attacker sends this modified request to the API endpoint.
* **The backend accepts the request**, and the unrelated user is now **linked** as a secondary user under the attacker’s business account.

### 4. Result of the Exploit

* The victim user appears in the attacker's "Manage Users" dashboard.
* Depending on how permissions are configured, the attacker might be able to:

  * Change their role.
  * Enable or disable specific access rights.
  * Potentially perform actions as if they are that user.
  * View internal business dashboards associated with that user.

---

## Why This Is a Serious Issue

### Affected Functionality

* **Business-level access controls**.
* **User privilege management**.
* **Internal trust model** between business accounts and users.

### Security Principles Violated

* **Lack of object-level authorization**: The API failed to verify if the user being referenced in the request belongs to the authenticated account.
* **Predictable identifiers**: If user IDs were incremental, it made brute-forcing or enumeration feasible.
* **Broken access control**: The backend did not enforce strict validation on cross-user actions.

### Potential Risks

| Risk                         | Description                                                            |
| ---------------------------- | ---------------------------------------------------------------------- |
| Unauthorized Account Linking | Users are added to organizations they don’t belong to                  |
| Privilege Escalation         | Attackers can assign roles and actions to other users                  |
| Account Manipulation         | May allow attacker to influence victim’s access or behavior            |
| Legal & Compliance Impact    | Violates user consent and access isolation guarantees                  |
| Data Exposure                | Possibility of accessing financial dashboards or sensitive information |

---

## Root Cause

The application failed to implement a **server-side check** to confirm that:

1. The `user_id` being added exists **within the same business entity** as the requestor.
2. The `user_id` or email submitted in the request is **authorized to be modified** by the current user.

These are standard **object ownership validation** rules that should be enforced at every sensitive API call.

---

## Remediation

After receiving the report, PayPal:

* Acknowledged and triaged the vulnerability.
* Added necessary **authorization checks** to ensure that:

  * Only users belonging to the business account can be added or modified.
  * Cross-business assignments are rejected.
* Updated severity during triage, reflecting the growing understanding of the issue’s impact.

No abuse was detected, according to PayPal.

---


### If you are a developer:

* Always enforce **object-level authorization**: authenticated ≠ authorized.
* Never trust client-supplied IDs for sensitive operations.
* Don’t rely on front-end restrictions to prevent ID tampering.
* Use **UUIDs** or other non-sequential identifiers to prevent brute-force enumeration.
* Log and monitor access to sensitive API endpoints.

### If you are a bug hunter:

* Look for areas where users can **modify IDs or references** in requests.
* Test for **cross-user actions**, such as assigning resources or modifying data.
* Combine predictable IDs with authorization bypass attempts.
* Use **Burp Suite** or browser tools to intercept and replay modified requests.
