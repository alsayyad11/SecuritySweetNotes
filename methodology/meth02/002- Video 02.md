
## Full Recon Workflow Using GitHub, Shodan, crt.sh, and More

**Target Example: AT\&T Bug Bounty Program**

This part of the recon methodology focuses on using open-source tools and smart filtering to perform **deep reconnaissance** on a bug bounty program, in this case **AT\&T**, by utilizing:

* Shodan (Free & Paid usage)
* GitHub Dorking
* crt.sh for SSL Cert-based subdomain discovery
* Default login panels & credential testing
* Avoiding result limits with creative free account rotation
* CVE-driven reconnaissance for newly released vulnerabilities

The video creator walks through each stage as if training new bug bounty hunters and shares techniques that are often overlooked.

---

## Step 1: Identify the Correct Organization Name

Before starting any recon, it’s essential to know what organization names and aliases are associated with the target. These names are used in certificate transparency logs and platforms like Shodan and Censys.

Examples:

* **AT\&T** → `AT&T Services Inc.`
* **Yahoo** → `Oath Inc.` or `Oath Holdings`
* **Uber** → `Uber Technologies Inc.`
* **Comcast** → `Comcast Corporation`

You can usually find this in:

* SSL certificates
* Legal footers on company pages
* WHOIS records

This ensures accurate scoping and avoids wasting time on irrelevant assets.

---

## Step 2: Discover Subdomains Using crt.sh

**Tool Used**: [crt.sh](https://crt.sh)

Steps:

* Input the organization name or main domain (e.g., `att.com`)
* Analyze the results for newly issued certificates, subdomains, and alternative domains (e.g., `attws.com`)
* Copy the relevant subdomains into your notes or recon tools

Note: AT\&T has **a massive number of subdomains**, so it’s best to prioritize based on keyword relevance or asset uniqueness.

---

## Step 3: Confirming Asset Ownership

To validate whether a domain or IP belongs to the intended program, the following checks are used:

### 1. SSL Certificate Inspection

* Inspect the certificate's **Subject** or **Issuer** fields
* Look for strings like `O=AT&T Services Inc.` or the program’s legal name

### 2. Use SSL Helper Tools

* Tools like:

  * SSL Helper
  * Censys
  * Shodan
* These help verify if a domain is linked to the correct organization

This step prevents mistakenly testing assets that are **out of scope**.

---

## Step 4: Shodan Recon – Free and Paid Techniques

### Basic Query Filters

Use search filters to narrow results. Example:

```bash
ssl:"att.com" http.status:200
```

You can also use:

* `org:"AT&T Services Inc"`
* `http.title:"login"`
* `product:"Apache Tomcat"`

### Free Account Limitations

Shodan’s free tier only shows **2 pages of results** per query. To work around this:

* Use additional filters to reduce result count (e.g., title or port)
* Switch between multiple free accounts (e.g., multiple Gmail, Twitter, or Microsoft logins)

> The creator mentions using **5+ accounts** before getting a paid subscription.

This allows viewing more results without breaching any terms of use.

---

## Step 5: Analyzing Shodan Results

Look for panels and services that are often **misconfigured or vulnerable**:

* Login pages (`/admin`, `/export`, `/portal`)
* Atlassian Jira dashboards
* Grafana, Jenkins, Jupyter Notebooks
* Directory listings
* Open development ports (e.g., 8080, 8443)

Shodan can also help identify:

* Technology stack
* Server banners
* Open ports and exposed services
* Default configuration files

---

## Step 6: Default Credentials Testing

After identifying a login panel:

* Test **default credentials** manually:

  | Username | Password |
  | -------- | -------- |
  | admin    | admin    |
  | admin    | password |
  | test     | test     |
  | guest    | guest    |
  | root     | root     |

* Use automation tools to scale:

  * **Nuclei** (for scanning and detecting default creds)
  * **Burp Suite Active Scanner**
  * **Quantix Scanner**
  * **Recon Engine**
  * **Aquatone**
  * **Naabu** (for port scanning)

Tools like Nuclei may detect banners like “Tomcat Manager App” and attempt default credentials automatically.

---

## Step 7: CVE & Zero-Day Hunting

If a new CVE is announced for a popular tech (e.g., Grafana, Atlassian Jira), you can:

1. Search Shodan using:

```bash
http.title:"Grafana"
```

2. Filter by company:

```bash
org:"AT&T Services Inc"
```

3. Identify active instances of the vulnerable version
4. Check the scope, and report ASAP if eligible

This method lets you **report critical bugs early**, especially before companies patch them.

---

## Step 8: Additional Subdomain Enumeration Tools

Besides crt.sh, the hunter uses:

### 1. [Whoxy](https://www.whoxy.com)

* Input domain or company name
* Returns associated domains (can be 2,000+)
* Free version gives limited results; full access requires an API

### 2. [SecurityTrails](https://securitytrails.com)

* Shows active and historical DNS data
* Helpful for mapping infrastructure (IPs, domains, MX records)
* Great for validating ownership and expanding recon surface

---

## Step 9: GitHub Reconnaissance

The hunter uses GitHub manually rather than automated tools.

### GitHub Dorks Used:

```bash
"att.com"
"att.com" password
"att.com" api_key
org:att
```

He searches for:

* Hardcoded secrets (keys, tokens, passwords)
* Internal URLs and APIs
* Configuration files or logs
* Developer notes and testing files

> Manual review helps catch leaks automated tools might miss.

---

## Step 10: Combining GitHub + Shodan + Default Auth

In one example, he:

1. Found a domain `dtveng.*` on GitHub
2. Verified it belongs to AT\&T
3. Found a login panel in Shodan
4. Used GitHub leaks and weak credentials
5. Gained access — confirming a valid vulnerability chain

This is an excellent example of **chaining recon sources** to uncover serious issues.

## Ethics Reminder

The hunter repeatedly emphasizes:

* Only target **in-scope** assets
* Use findings from Shodan/GitHub as **intel**, not attack vectors unless confirmed to be in-scope

This is essential to stay within responsible disclosure guidelines and avoid legal issues.
